## 4. Recuperación administrativa independiente de SQL

### Precondiciones y material de recuperación

La comprobación documental se basa en: acceso Docker QA autorizado, UID postgres con acceso al archivo/PGDATA, pg_ctl 17.11, PID file disponible y configuración en volumen de directorio RW, no un HBA bind-mount individual. Esto permite reemplazar HBA y señalar al postmaster desde el SO sin login PostgreSQL. **No se ensayó reemplazo ni recarga real.**

Antes de modificar HBA en C2 deben existir, fuera de Git, con directorio 0700 y archivos 0600:

1. Copia íntegra del HBA realmente activo en disco, con SHA-256, fecha, destino QA y ownership/modos registrados.
2. Copias de postgresql.conf y postgresql.auto.conf; inventario de includes de configuración/HBA y copia de todo archivo incluido que vaya a cambiar. No inferir ausencia de includes únicamente por el listado actual de filas.
3. ACL/ownership/defaults previos mediante consultas de lectura, sin datos hospitalarios ni verificadores. Configuración cliente no secreta y diff del cambio Pool para reversión de código independiente.
4. HBA definitivo de cambio y HBA de recuperación identificados por hash, revisados con los orígenes reales y reglas de administración acordadas. No copiar la plantilla C1.1 sin render.
5. Responsable operativo con Docker disponible y autorización de contingencia, canal secreto bootstrap verificado por el custodio y dos sesiones A/B cuando se autoricen pruebas. No copiar contraseña bootstrap al paquete de configuración.

El directorio propuesto aún no existe: no hay respaldo C2 verificado ni hash de una copia para restaurar. El volumen es persistencia de estado, no sustituto de respaldo. Un backup de configuración no es un backup físico consistente de la base; no copiar PGDATA completo en caliente ni restaurarlo para un incidente HBA.

Los backups originales contienen trust. Restaurarlos exige aprobación explícita de contingencia porque devuelve esa exposición. Una recuperación segura con SCRAM necesita contraseña bootstrap válida; una restauración HBA no repara una contraseña ausente/incorrecta. No se introduce peer/pg_ident, otro superusuario, single-user mode o trust nuevo como arreglo improvisado.

### Procedimiento propuesto ante bloqueo de nuevos logins

**Todo lo siguiente es propuesta para autorización posterior. No ejecutar durante C1.2.**

1. Detener la secuencia C2 y cualquier provisión adicional. Conservar A; no cerrar sesiones administrativas ni reiniciar servidor. Registrar fallo sin contraseña ni volcar consultas/capturas de autenticación.
2. Confirmar contenedor/volumen/PID/UID vigentes y comparar hashes de copia, candidato y archivo instalado. Si hubo cambios ajenos o el respaldo no coincide con el manifiesto, detener la restauración automática y escalar al custodio QA.
3. Preferir corrección revisada que conserve SCRAM si la causa es una dirección/usuario erróneo y la contraseña está verificada. Si se requiere restaurar HBA original con trust, obtener la aprobación de contingencia previamente definida. No ampliar a host all all all trust.
4. El operador Docker restaura únicamente el HBA autorizado, de forma atómica dentro del mismo PGDATA, usando UID postgres, modo 0600 y sin seguir enlaces. La sustitución por rename conserva la consistencia del archivo frente a lectores. No sobrescribir postgresql.conf/auto.conf si no cambiaron.
5. Solicitar recarga con pg_ctl como postgres, sin usar credencial SQL. Verificar archivos/hashes, errores de carga y una nueva conexión administrativa B por cada ruta requerida cuando esas pruebas estén autorizadas. No basta el código de salida de pg_ctl.
6. Si se recuperó, documentar causa y detener C2 para revisar candidato y exposición residual. Si no se recuperó, no repetir cambios ciegos: declarar incidente QA y mantener el estado para el responsable. Si postmaster murió, Docker no está disponible o el volumen está RO/lleno, esta vía no basta; un arranque o reparación de almacenamiento requiere autorización distinta.

Ejemplo concreto revisable de restauración, condicionado a backup seguro existente, hash aprobado, archivo regular y padres confiables; no está listo para copiar/ejecutar sin esos controles:

```sh
# PROPUESTA MODIFICADORA, NO EJECUTADA. Ruta de backup pendiente de creación/verificación.
docker exec -i --user postgres sigeh-qa-b1-postgres-qa-1 sh -c '
set -eu
umask 077
test ! -L /var/lib/postgresql/data/pg_hba.conf
test ! -e /var/lib/postgresql/data/pg_hba.conf.c2-restore
test ! -L /var/lib/postgresql/data/pg_hba.conf.c2-restore
cat > /var/lib/postgresql/data/pg_hba.conf.c2-restore
chmod 0600 /var/lib/postgresql/data/pg_hba.conf.c2-restore
c2_digest=$(sha256sum /var/lib/postgresql/data/pg_hba.conf.c2-restore)
test "${c2_digest%% *}" = "$1"
mv /var/lib/postgresql/data/pg_hba.conf.c2-restore /var/lib/postgresql/data/pg_hba.conf
' sh HBA_SHA256_APROBADO < /home/robreport/.local/share/sigeh-c2-recovery/pg_hba.conf.before
# Revisar SHA-256 instalado y ownership 70:70 antes de la recarga propuesta:
docker exec --user postgres sigeh-qa-b1-postgres-qa-1 /usr/local/bin/pg_ctl -D /var/lib/postgresql/data reload
```

Sustituir HBA_SHA256_APROBADO por los 64 dígitos del manifiesto validado; no obtenerlo del flujo recibido sin contrastarlo con ese manifiesto. La comprobación dentro del contenedor impide instalar un flujo truncado que cat pudiera aceptar como EOF normal. La ejecución debe comprobar tamaño/contenido/hash de backup y candidato antes del reemplazo. Ante error de transmisión o fichero temporal residual no continuar: revisar y retirar solo ese temporal con autorización. PGDATA no puede ser escribible por usuarios no confiables; el ejemplo no es resistente a un adversario que ya controle la cuenta postgres. No usar root para dejar HBA con owner incorrecto. No se escribe en postmaster.pid ni se confunde PID 1 del contenedor con PID 1 del host.

`pg_ctl reload` envía SIGHUP y relee configuración sin reiniciar ni necesitar login SQL; relee también otros archivos de configuración, por lo que se debe congelar cualquier edición concurrente. [pg_ctl PG17](https://www.postgresql.org/docs/17/app-pg-ctl.html).
